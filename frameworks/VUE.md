# Keyframery for Vue: conventions

Every Vue component must look, move and behave like its React original in src/components, in Subtle and Springy
(MOTION.md, last section). React is the source of truth; never edit src/.

## What a user installs (mirrors React)

```
components/keyframery/<slug>/<Part>.vue   one SFC per exported part (the shadcn-vue layout)
components/keyframery/<slug>/index.ts     exports every part, with the SAME names as the React exports, plus types
components/keyframery/core/<slug>-core.ts the React core file, copied as is (it is framework-free), import alias rewritten
lib/keyframery.ts                         speed for Vue: provide/inject + KeyframeryProvider (frameworks/vue/_lib)
lib/utils.ts                              cn (clsx + tailwind-merge)
```

## Where things live in this repo

- `frameworks/vue/<slug>/`: GENERATED by scripts/frameworks/generate.mjs. Never hand-edit.
- `frameworks/overrides/vue/<slug>/`: HAND-WRITTEN. When this folder exists, the generator copies it to
  `frameworks/vue/<slug>/` instead of generating. Use it for components generation can't carry (JS-heavy native ones)
  and for every core-built component (createParts).
- `frameworks/vue/_lib/`: shared lib (keyframery.ts, utils.ts) and `keyframery.css` (tokens and the five motion styles
  only, like React's motion.json). Each component ships its own kf-* keyframes / `@property` blocks in a non-scoped
  `<style>` in its root SFC (generated: from React's `<style href>` blocks; overrides: written by hand).
- `node scripts/frameworks/generate.mjs <slug>…` regenerates only those Vue components (+ _lib); svelte/solid/web are
  written only by a full run (no slug). A slug with no classes json is copied from its override.
- `frameworks/test/vue/`: the Vite + Tailwind test app (Vue 3.5, @ui-sdk/vue + @ui-sdk/core 0.1.0-beta.17).

## Rules for every part

- `<script setup lang="ts">`, Vue 3.5. Render UI SDK's own Vue part (`@ui-sdk/vue/<component>`), or for a
  component UI SDK doesn't ship, `createParts(definition, {...})` from `@ui-sdk/vue/primitive` with the definition
  from the copied core file, exactly like the React primitive does with `@ui-sdk/react/primitive`.
- Classes: the React primitive's classes then the ui layer's, merged with `cn`, then the user's `class` last
  (`inheritAttrs: false`, `cn(base, attrs.class)`). Same Tailwind strings, character for character.
- Props: everything the UI SDK Vue part takes, passed through, plus our extras with the same names and defaults as
  React (`speed`, `variant`, `size`, `presentation = "auto"` on Popover/Menu/Select/Combobox/Autocomplete/DatePicker…).
- Content that depends on state (React's `children(state)` / `className(state)`): a scoped default slot
  `v-slot="{ state }"` (UI SDK's Vue parts pass `{ state }`) and a class function where the part supports one.
- Render props become named slots, UI SDK-style: `render={<El/>}` → `#render="{ props }"`, `renderToken` → `#token`,
  JSX props like `fallback` → `#fallback`. Function props that return markup (data-table `cell`, markdown
  `components`) stay props returning `h()` vnodes.
- Extra elements the React ui layer renders (chevrons, check marks, key copies, spinners): render them in the SFC.
- `speed`: the root provides it (`provide(speedKey, value)`) and sets `--kf-speed` on itself; parts that render in
  a portal (popups) `inject` it and set `--kf-speed` on themselves, like React's useSpeedStyle.
- JS timings (timers, rolls, readiness gates): port them with the same durations × speed × flourish.
- Agent: keep every agent-facing label and data-* attribute React has.
- Never add a dependency React doesn't have (except vue, @ui-sdk/vue).

## Typed props

Every part forwards the user's props to UI SDK's part as attrs (behaviour stays exactly UI SDK's) and declares
them as a type only, so vue-tsc and Volar check and complete them in the user's templates:

```vue
<script lang="ts">
import type { PartProps } from "@/lib/keyframery"
import type { Tabs as SdkTabs } from "@ui-sdk/vue/tabs"
type OwnProps = { speed?: Speed }                       // our extras: real props, React's defaults
export type TabsProps<A extends string = string, B = unknown> = Omit<PartProps<typeof SdkTabs<A, B>>, keyof OwnProps> & OwnProps
</script>
<script setup lang="ts" generic="A extends string = string, B = unknown">
const props = defineProps<OwnProps & /* @vue-ignore */ TabsProps<A, B>>()   // @vue-ignore: no runtime props
```

- `PartProps<typeof X>` (lib/keyframery.ts): what UI SDK's Vue part takes in a template: its props, its events as
  `on*` props (`onValueChange`, `"onUpdate:value"` for `v-model:value`) and its element's attributes.
  `ElementProps<"div">`: the attributes of a plain element, for parts that render one.
- Generic UI SDK parts (Tabs, Accordion, AccordionItem, SelectItem, ComboboxItem, ListboxItem, TriggerMenuItem)
  make the SFC generic with the same parameters, so `:value` keeps its inferred type.
- Each `<Part>Props` type is exported from the SFC and from the component's index.ts (`import { type TabsTabProps }
  from "@/components/keyframery/tabs"`). It shadows the same-named core type `export *` brings in (a superset).
- Overrides: do the same, or reuse a generated type (`import type { PopoverContentProps } from "../popover"`).
- frameworks/test/vue/typecheck/PropsTypes.vue proves it: right props must pass, wrong ones sit under
  `@vue-expect-error`, so `pnpm exec vue-tsc --noEmit` fails if typing regresses. The test app's tsconfig is the one
  `npm create vite -- --template vue-ts` gives (strict, noUnusedLocals/Parameters, erasableSyntaxOnly, lib ES2022):
  no unused locals, no enums/namespaces, no ES2023+ methods (findLastIndex, toSorted…).

## Parity bench

`node scripts/frameworks/bench-parity.mjs <slug>…` compares every React example with its Vue port
(frameworks/bench/examples/vue/) in Subtle and Springy and writes frameworks/bench/report.md plus side-by-side shots.
A component is done when its rows say identical.

## Checks you run before handing over

- `pnpm exec vue-tsc --noEmit` in frameworks/test/vue for your components (add vue-tsc there if missing).
- Render each of your components in the test app on YOUR assigned port only, in Subtle and Springy, and compare it
  with the React lab (http://localhost:4610/#/<slug>, `?play=off`, `?motion=subtle|springy`) by computed style per
  data-slot and by looking. Stop your dev server when done.
- No git write commands. Touch only the paths your brief lists.

## UI SDK Vue issues (to file upstream)

### Drawer `side="right"` opens on the left under `dir="rtl"` (@ui-sdk/vue 0.1.0-beta.17)

Repro: `<html dir="rtl">`, then
`<Drawer side="right"><DrawerTrigger>Open</DrawerTrigger><DrawerContent>…</DrawerContent></Drawer>` from
`@ui-sdk/vue/drawer`, open it. The sheet sits at the left edge; with `@ui-sdk/react` it sits at the right.

Cause: core's `styleHost` (`@ui-sdk/core/dist/foundation/popups/sheet.js`) picks `justify-content` from
`getComputedStyle(host).direction`. In Vue it runs while the viewport `<div>` is still detached (`isConnected`
false, no `data-slot` yet), so the direction reads `""`, not `"rtl"`, and `side="right"` gets `flex-end`, which is
the left in a right-to-left row. In React the host is already in the page and reads `rtl` (`flex-start`).

Our fix until UI SDK fixes it: scripts/frameworks/vue-parts/drawer/style.css, added to Drawer.vue's `<style>`:
`[data-slot="drawer-viewport"][data-side="right"]:dir(rtl) { justify-content: flex-start !important }` and the mirror
for `left`. It sets the value UI SDK means, so it stays correct after the upstream fix. Generator hook:
`vue-parts/<slug>/style.css` is appended to the component's own `<style>` block.

### Command with `items`: React shows no highlight at rest, Vue highlights the first command

UI SDK's command list is `autoHighlight: "always"` (core `command-api.js`), and both frameworks highlight the first
command when the commands are children (command/01-basic). With `items` (command/04-data), React's commands mount in
a later render than the list settles, so nothing is highlighted until you type or press a key; Vue's mount in the
same pass and get the documented highlight. Behaviour difference in UI SDK's adapters, not in our parts; Vue follows
the documented behaviour.
